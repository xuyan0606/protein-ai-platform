# KWB-EnzymeDesigner 研发计划

## 研发目标

在现有酶蛋白 AI 平台基础上，研发一个科为博自有的多任务酶改造模型 `KWB-EnzymeDesigner`。

对外表现为一个统一模型能力：

```text
输入：酶序列 / 结构 / 底物 / 目标 / 实验条件 / 历史证据
输出：候选突变排序 + 稳定性预测 + 活性风险 + 底物适配 + 实验成功率 + 证据链
```

工程上先作为平台工具接入，不替换现有 GPT-5.6 主控模型。

## 研发原则

- 本地优先：未收到明确指令，不同步服务器。
- 先合同后模型：先稳定输入输出 schema，再做算法。
- 先规则 MVP 后训练模型：优先复用现有工具和 KWB 数据，形成可验证闭环。
- 先评测后上线：每个模型版本必须跑固定 benchmark。
- 结论可追溯：所有分数、候选突变和风险判断都要能追溯证据来源。
- 不做黑盒单分数：保留多头评分和置信度。

## 总体架构

```text
GPT-5.6 主控层
  -> KWB-EnzymeDesigner 工具模型
      -> mutation_rank_head
      -> stability_head
      -> activity_risk_head
      -> substrate_fit_head
      -> assay_success_head
  -> KWB-EnzymeDB 证据层
  -> 现有结构/注释/MD/配体工具链
  -> 证据分层报告
```

## 阶段 1：数据对象标准化

时间：第 1-2 周

目标：
把平台中的酶、结构、底物、突变、实验条件、证据统一成 `KWB-EnzymeCase` 对象。

数据字段：
- 酶名称、EC 编号、UniProt ID、PDB ID。
- 序列、结构来源、结构置信度。
- 底物、反应、pH、温度、buffer、表达体系。
- 突变列表、单点/组合突变、编号体系。
- 实验指标：活性、kcat、Km、Tm、半衰期、表达量、可溶性。
- 证据来源：KWB 私有数据、公开数据库、文献、工具预测、人工审核。

交付物：
- `datasets/case_schema.md`
- `datasets/sample_case.json`
- 数据质量评分规则。

验收标准：
- 至少覆盖 5 类真实业务场景。
- 每个样本能标记证据来源和数据版本。
- 能区分缺失字段、预测字段和实验字段。

## 阶段 2：Benchmark 评测集

时间：第 2-3 周

目标：
建立固定评测集，防止模型只会生成好看的报告。

第一批评测任务：
- 低 pH 淀粉酶稳定性改造。
- 脂肪酶底物选择性改造。
- 热稳定性提升。
- 活性提升但避免破坏稳定性。
- 上传 PDB 后残基编号映射。
- 配体/底物口袋突变推荐。

交付物：
- `benchmarks/cases/`
- `benchmarks/eval_protocol.md`
- `benchmarks/scorecard.md`

验收标准：
- 每个案例有输入、期望行为、禁忌行为、评分标准。
- 覆盖“序列级 / 预测结构 / 实验结构 / 私有数据证据”分层。

## 阶段 3：规则 + 数据驱动 MVP

时间：第 3-5 周

目标：
不先训练模型，先用现有工具和数据库做一个可运行 MVP。

复用工具：
- `annotation_bundle`
- `residue_numbering_gate`
- `structure_search_foldseek`
- `mutation_priority_score`
- `mutation_epistasis_check`
- `ligand_preprocess`
- `gromacs_md`
- `data_lookup`

输出：
- 候选突变表。
- 多头评分。
- 风险标签。
- 证据引用。
- 下一轮实验建议。

交付物：
- `prototype/kwb_enzyme_designer_mvp.md`
- 本地 mock 输入输出样例。
- 与现有 `ToolRegistry` 的接入设计。

验收标准：
- 对同一输入输出稳定。
- 不伪造结构或实验结论。
- 上传结构时必须先过结构和编号门控。
- 仅序列时结构相关结论必须等待结构预测或标记为未验证。

## 阶段 4：本地模型服务原型

时间：第 5-6 周

目标：
把 MVP 封装为本地 HTTP 服务，后续方便接入平台工具层。

接口：
- `GET /health`
- `POST /v1/enzyme-design`

交付物：
- `prototype/service_api.md` 完整化。
- 本地服务最小实现。
- 本地 smoke 测试。

验收标准：
- 输入符合合同。
- 输出符合合同。
- 错误路径返回结构化 `blocked/failed` 原因。

## 阶段 5：训练数据构建

时间：第 6-8 周

目标：
把工具调用、KWB 数据库、实验反馈整理成训练数据。

训练数据来源：
- KWB Lipase Evidence DB。
- 平台实验反馈。
- 工具调用审计。
- benchmark 真实案例。
- 公开数据库和文献抽取的弱标签。

交付物：
- `datasets/curated/` 目录规范。
- 样本脱敏流程。
- 训练/验证/测试划分策略。

验收标准：
- 样本能追溯来源。
- 成功和失败样本都保留。
- 明确哪些字段可训练，哪些字段只做证据展示。

## 阶段 6：第一版 KWB 小模型

时间：第 8-10 周

目标：
先训练最有业务价值的两个 head：

- `mutation_rank_head`
- `stability_head`

输入特征：
- 序列 embedding。
- 结构位置特征。
- 残基环境。
- 注释和保护位点。
- 历史突变证据。
- 实验条件。

交付物：
- 模型训练记录。
- 模型版本卡。
- benchmark 结果。

验收标准：
- 在固定 benchmark 上优于规则 MVP。
- 能输出置信度。
- 不推荐已知催化核心禁忌位点。

## 阶段 7：多头模型扩展

时间：第 10-12 周

目标：
补齐剩余三个 head：

- `activity_risk_head`
- `substrate_fit_head`
- `assay_success_head`

交付物：
- 多头输出合并逻辑。
- score calibration。
- Go / Watch / No-Go 决策规则。

验收标准：
- 能解释各 head 分数对总分的贡献。
- 能在证据不足时降级输出，不假装确定。
- 能给出下一轮实验建议。

## 阶段 8：平台本地接入设计

时间：第 12 周后

目标：
设计如何接入现有平台，但不自动部署。

接入点：
- 后端工具：`backend/app/tools/kwb_enzyme_designer.py`
- 工具注册：`ToolRegistry._TOOL_MODULES`
- Agent 规划：结构门控后调用 KWB 模型。
- 前端展示：模型运行时间线、多头评分面板、证据来源面板、结构位点高亮。

验收标准：
- 本地测试通过后，再由用户决定是否上线。
- 未收到上线指令前不执行服务器同步。

## 风险和对策

| 风险 | 对策 |
|---|---|
| 私有实验数据量不足 | 先做规则 MVP 和弱监督，逐步积累反馈 |
| 数据字段不统一 | 先定义 `KWB-EnzymeCase`，导入前做质量评分 |
| 模型输出看似高级但不可验证 | 强制证据分层和 benchmark |
| GPT-5.6 与 KWB 模型职责混乱 | GPT-5.6 做主控，KWB 模型做专业评分 |
| 结构依赖分析提前执行 | 强制结构门控和编号门控 |
| 上线影响现有平台 | 本地-only 研发，后续小步接入 |
