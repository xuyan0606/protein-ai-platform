# 酶改造 AI 平台全量整改波次设计

## 目标

将当前聊天式分析平台推进为可强制执行、可验证、可追溯的酶改造工作流；所有未满足的整改项均被纳入可测试的工作包，外部依赖项不伪造为已完成。

## 工作包与顺序

### A. 治理闭环

固化脱敏的 `conv_78`、`conv_225`、`conv_226` 症状回归；将运行态、身份一致性、报告完成门槛和各工作流策略收敛为任务契约。完成标准是：追问不重跑，输入补充/目标切换可区分，身份冲突和报告缺项均进入 `NEEDS_REVIEW`。

### B. 工具体系

以运行时 `/api/tools` manifest 作为线上事实源，并建立交付包目录条目到“在线可用 / 替补降级 / 不适用 / 待接回”的明确映射。优先治理 8 个护栏工具。工具不能自动接回时，必须在策略和用户可见输出中标为 `DEGRADED`。

### C. 可靠性

前端请求、SSE 流和服务健康检查形成同一错误契约：连接拒绝、超时或异常中断必须显示“服务暂不可用，请稍后重试”，并保留诊断编号；不得以空白界面或静默完成呈现。

### D. 运行能力与验收

ESM-2/torch、GPU 和外部工具依赖采用只读就绪度检查与 smoke test 验证。缺少运行依赖时报告 `blocked`，不声称模型已可用。线上验收只在用户授权部署并提供环境后执行。

## 关键数据契约

每次任务响应至少包含：`intent`、`session_id`、`intake_status`、`workflow_id`、`route_reason`、`final_status`、`trace[]`、`fallback_trace[]`。身份冲突补充 `identity_consistency`；报告门槛失败补充 `report_quality_violations[]`。

工具基线 manifest 至少包含版本、运行时工具数量、排序工具名称 hash 和来源。缺失工具台账的每一行包含 `tool_id`、`desired_state`、`runtime_state`、`configured_fallback_tool`、`fallback_tool`、`fallback_level`、`owner_action`；其中 `configured_fallback_tool` 只表示配置候选，`fallback_tool` 仅在候选在线且实际可用时出现。

## 错误处理与安全边界

- 工具失败、阻断、缺参数、超时均进入 trace；工具替补必须留痕并向用户说明。
- 不完整的策略 catalog 仅执行已确认的禁止边界；完整 allowlist 启用前不误阻断 legacy 分析。
- 不连接、不部署、不安装依赖即可完成的本地整改将直接实施。
- 修改线上环境、下载模型权重、安装 torch、接回外部服务或执行真实任务前，需要相应环境与授权；该类任务先产出可执行检查与验收记录。

## 验收

1. 脱敏真实会话场景全部通过并覆盖续问、输入补充、目标切换和概念问答。
2. 每个工作流存在明确的工具策略状态；未完成 catalog 的风险可见。
3. 工具目录、运行时 manifest 与缺失台账能够自动对账。
4. 服务断连和 SSE 中断在前端有可见中文提示。
5. ESM-2/torch 就绪度与真实 smoke test 结果可审计。
6. 全量本地回归、编译、静态差异检查通过；线上验收单独记录真实环境结果。
